troubleshoot Investigações guiadas

Roteiros de raciocínio — sugerem comandos e explicam a decisão. O framework não executa nada nem conhece a sua máquina.

wifi_off "Estou sem acesso à internet"
  1. Tenho IP e gateway? Windows ipconfig /all · Linux ip a + ip route. Sem IP válido ou sem rota padrão, o problema é local (DHCP/config).
  2. O gateway responde? ping 192.168.1.1. Se não responde, o problema está entre você e o gateway (cabo/Wi-Fi/switch).
  3. Chego num IP externo? ping 8.8.8.8. Responde por IP mas não por nome → é DNS. Não responde por IP → roteamento/enlace.
  4. O nome resolve? Windows Resolve-DnsName example.com · Linux dig example.com. Falha aqui confirma DNS.
dns "O nome não resolve"
  1. Qual resolvedor estou usando? Linux dig example.com mostra o SERVER que respondeu; Windows ipconfig /all lista os servidores DNS.
  2. É o meu resolvedor ou o nome? Teste um resolvedor público explícito: dig @8.8.8.8 example.com. Resolve com ele mas não com o seu → problema no resolvedor local.
  3. É cache? Compare com outro host; TTL alto pode manter resposta antiga por um tempo.
door_front "Não consigo acessar uma porta"
  1. O nome resolve? Se não, resolva o DNS primeiro (não adianta testar a porta de um nome que não vira IP).
  2. O host responde? ping (lembrando: ICMP pode ser bloqueado — não responder não prova nada).
  3. A porta abre daqui? Windows Test-NetConnection host -Port 443 · Linux nc -vz host 443. Falha pode ser firewall, rota ou serviço parado — não conclua a causa só disso.
  4. Onde está o serviço? No próprio host, veja se algo escuta a porta: ss -tulpn / netstat -ano.
hearing "Quero descobrir qual processo está ouvindo"
  1. Liste as portas em escuta com o PID. Windows netstat -ano · Linux ss -tulpn.
  2. Ligue o PID ao programa. Windows netstat -anob (admin) ou Get-Process -Id PID · Linux sudo ss -tulpn / sudo lsof -i.
  3. Confirme a legitimidade. O nome do processo pode ser forjado: verifique o caminho do binário, a origem e o hash antes de confiar.
