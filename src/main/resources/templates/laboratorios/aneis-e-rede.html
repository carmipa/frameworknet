memory Da aplicação até a placa de rede

Todo pacote que sai do seu computador nasce numa aplicação sem privilégio e só chega à rede depois de cruzar a fronteira mais vigiada do sistema: a passagem do Ring 3 (aplicação) para o Ring 0 (kernel). Aqui você entende essa fronteira e simula o percurso.

scienceSimulação didática: esta página explica e anima o conceito — ela não cria sockets, não envia nem captura pacotes e não altera esta máquina.
{! ---------- 1. Conceito: o que sao aneis de privilegio ---------- !}

donut_large 1. O que são anéis de privilégio

A CPU x86 não confia igualmente em todo código que executa. Ela separa a execução em níveis concêntricos de privilégio — os Protection Rings. Quanto mais interno o anel, mais a CPU permite: acessar memória física, falar com o hardware, mascarar interrupções. Quanto mais externo, mais a CPU barra. É essa barreira, gravada em silício, que impede uma aba do navegador de reprogramar sua placa de rede ou ler a memória de outro processo.

Ring 3
web User Mode — menor privilégio

Onde roda tudo que você usa: navegador, curl, o backend deste site. Cria sockets pela API POSIX/libc (socket(), connect(), send()), mas não toca a NIC — precisa pedir ao kernel.

Ring 1·2
history Intermediários — quase sem uso hoje

Pensados para drivers e sistemas como o OS/2. Na prática caíram em desuso; o exemplo real foi a virtualização Xen paravirtual (PV), que rodava o kernel convidado no Ring 1 no x86 de 32 bits. Em x86-64 (long mode) a segmentação que os sustentava é desativada — sobram, de fato, só o Ring 0 e o Ring 3.

Ring 0
settings Kernel Mode — máximo privilégio

O kernel do sistema operacional: escalonador, memória física, drivers. É aqui que vive a pilha TCP/IP real — tratamento da interrupção da NIC, montagem do sk_buff (Linux), Netfilter, filas de saída (qdisc).

lightbulb

O “aha” moderno: os quatro anéis são história de projeto. O hardware atual usa, na prática, apenas dois — Ring 0 e Ring 3. Toda a segurança do dia a dia mora na fronteira entre esses dois.

{! ---------- 2. Por que a rede cruza a fronteira ---------- !}

swap_vert 2. Por que a rede cruza a fronteira

Quando a aplicação chama send(), ela executa uma instrução syscall que transfere o controle para o kernel, num endereço fixo apontado pelo registrador especial MSR LSTAR. A CPU sobe para o Ring 0, o kernel valida o pedido e só então age. Detalhe que quase todo material erra: cruzar a fronteira de syscall é uma troca de modo (privilégio), não necessariamente uma troca de contexto completa do escalonador (troca de processo) — são coisas diferentes.

shield_person Portas < 1024 são privilegiadas

Associar uma porta baixa (ex.: 80, 443) exige a capability CAP_NET_BIND_SERVICE. Não é lei física: é política do kernel — o sysctl net.ipv4.ip_unprivileged_port_start pode até baixar esse limite.

radar Raw sockets exigem poder

Para forjar um pacote inteiro (cabeçalho IP/ICMP à mão — scanners, geradores de tráfego, ferramentas didáticas de captura) o Ring 3 precisa de CAP_NET_RAW (ou root). É por isso que o Ring 0 barra isso por padrão.

bolt syscall × int 0x80

O Linux x86-64 moderno entra no kernel pela instrução syscall (rápida, via LSTAR). A interrupção int 0x80 é o caminho legado de 32 bits, mais lento — mesmo destino, época diferente.

verified_user O kernel não confia no usuário

Ponteiros e bytes vindos do Ring 3 passam por copy_from_user e por barreiras de hardware como o SMAP — o kernel nunca acessa memória do usuário por acidente.

{! ---------- 5. O caminho de volta (RX) ---------- !}

u_turn_left 5. O caminho de volta (recepção)

Na chegada, o percurso se inverte — e mostra por que é o Ring 0 quem atende o hardware. A NIC recebe o quadro e dispara uma interrupção; o kernel responde e, sob tráfego intenso, ativa o NAPI (troca interrupção por polling em softirq) para não afogar a CPU. Os bytes sobem a pilha como sk_buff, passam por Netfilter e roteamento, chegam ao buffer do socket — e só então a aplicação no Ring 3 os lê com recv()/read(). A aplicação nunca “pega” o pacote do fio: ela recebe uma cópia que o kernel já validou.

{! ---------- 6. Alem dos aneis classicos ---------- !}

layers 6. Além dos anéis clássicos

A comunidade de segurança fala em “anéis negativos”. Cuidado: não são anéis x86 formais — são contextos de privilégio adicionais, apelidados assim por ficarem “abaixo” do kernel.

Ring −1
dns Hipervisor (VMX root)

Onde rodam KVM, ESXi, Hyper-V. Controla os kernels convidados “acima” dele.

Ring −2
memory_alt SMM — System Management Mode

Firmware da placa-mãe (UEFI), entrado por uma SMI, em SMRAM. Opaco até para o kernel.

Ring −3
developer_board Intel ME / AMD PSP

Um processador independente da CPU principal, com seu próprio firmware. Nem é “um anel da CPU” — é outro hardware.

rocket_launch

E o “kernel bypass” (DPDK / eBPF / AF_XDP)? Ele reduz o custo de cruzar a fronteira, mas não elimina o Ring 0: ainda depende do kernel (VFIO/IOMMU, hugepages, root) para mapear a NIC. O que muda é que parte da pilha de rede passa a rodar no Ring 3 (DPDK) ou como código verificado dentro do kernel (eBPF). A regra dos anéis não é burlada — é reorganizada.
